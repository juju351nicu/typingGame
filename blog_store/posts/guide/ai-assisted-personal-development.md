# AIを活用して個人開発を進めた記録

typingGame の開発では、ChatGPTやClaude CodeのようなAIを、実装の相談相手として使いました。

ただし、AIにすべて任せるのではなく、作業単位を小さく分け、最後は自分で確認してから進めることを意識しました。

## AIに任せたこと

AIには主に、次のような作業を手伝ってもらいました。

- 実装方針の整理
- 既存コードの読み取り
- 影響範囲の洗い出し
- テスト観点の提案
- エラー原因の切り分け
- READMEや開発メモの整理
- Gitコマンドの次手順確認

特に助かったのは、長くなった作業を「今どこまで終わっていて、次に何を見るべきか」に分解できたことです。

個人開発では、実装そのものよりも、作業の現在地が分からなくなることがあります。
AIにログや差分を見てもらい、次の1手を整理することで、途中で止まらず進めやすくなりました。

## 自分で判断したこと

AIを使うときに大事だと感じたのは、判断まで丸投げしないことです。

例えば、`npm audit fix --force` のように大きな更新を促される場面では、そのまま実行せず、Vite更新タスクとして分けました。

また、GitHub Pages公開時も、バックエンドAPIをすぐ有効にするのではなく、まずはAPI無効モードでフロントエンド単体を安定公開する方針にしました。

AIは候補を出すのが得意ですが、プロジェクトの目的や学習の順番を決めるのは自分です。

## 確認を省略しない

AIと進める場合でも、最後の確認は必ず自分で行うようにしました。

実際に使った確認は次のようなものです。

```bash
npm run test
npm run build
npm audit
git status
gh run list --workflow "Deploy to GitHub Pages" --limit 3
```

公開後は、ブラウザで実際にゲームをプレイし、Result表示、localStorage保存、ランキング表示も確認しました。

コードが生成できても、動いていることを自分の目で確認しないと、ポートフォリオとして安心して見せられないからです。

## 引き継ぎ資料を残す

AIと長く作業すると、会話が長くなり、前提が分かりにくくなることがあります。

そのため、節目ごとに引き継ぎ資料を更新しました。

- 完了した作業
- 未完了の作業
- 次回最初に確認すること
- 重要な設計判断
- 実行済みのテスト
- 失敗したコマンドと原因

これにより、次回再開時に同じ説明を繰り返さずに済みました。

## 学んだこと

AIは、個人開発の速度を上げるだけでなく、作業を整理するためにも役立ちます。

一方で、AIが出した内容をそのまま採用すると、プロジェクトの目的からずれることもあります。

自分がやりたいことを決め、AIには調査、整理、実装補助、確認手順の作成を手伝ってもらう形が、自分には合っていました。

今後も、AIを「代わりに作る人」ではなく、「一緒に考える相手」として使いながら、実装力と判断力の両方を伸ばしていきたいです。
