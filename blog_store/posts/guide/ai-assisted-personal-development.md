# AIに調査・整理・実装補助を任せ、技術判断は自分で行う個人開発の進め方

typingGameの開発では、ChatGPTやClaude CodeのようなAIを実装の相談相手として使っています。

ただし、AIが提案した内容をそのまま採用することはしていません。調査、整理、実装補助はAIに任せますが、案の採否とプロジェクトの方針に関わる判断は自分で決める、という線引きにしています。

この記事では、その線引きを実際の作業でどう適用したのかを、2つの具体例とあわせてまとめます。

## 作業の進め方

1つの作業は、次の流れで進めています。

```text
やりたいことを自分で決める
        ↓
AIへ既存コードの調査と影響範囲の洗い出しを依頼
        ↓
AIが対応案を提示
        ↓
採用・却下を自分で判断（ここは任せない）
        ↓
実装
        ↓
自分でdiffを読む
        ↓
npm run test / npm run build
        ↓
公開後にブラウザで動作を見る
```

重要なのは、AIが関わる範囲を「調査」「案の提示」「実装補助」までとし、採否の判断、diffの確認、テスト、最終判断は自分の側に残していることです。実装そのものをAIに手伝わせるかどうかは効率の問題ですが、採否と検証を渡してしまうと、動いている理由を説明できないコードが残ります。

## 例1: npm audit fix --force を採用しなかった

`npm audit` を実行したところ、Viteが依存する開発サーバー周りの脆弱性が検出されました。npmの出力にも、AIの提案にも `npm audit fix --force` が挙がっていました。

これを実行すればその場では0件になります。しかし `--force` はメジャーバージョン更新を含む破壊的な変更が入る可能性があり、当時はGitHub Pagesの公開作業と並行していました。

そこで、次のように判断しました。

- 公開作業とは別タスクとして切り出す
- `--force` は使わず、Viteと `@vitejs/plugin-vue` を明示的に更新する
- 更新後に既存テストとGitHub Pages用ビルドを通す

結果として、更新後に `npm audit` は0件になりましたが、ローカルでは通るのにGitHub Actionsの `npm ci` が失敗するという別の問題が出ました。これはlockfileのoptional dependency不足が原因で、CI相当のnpmバージョンで再現させてから同期しています。

もし `--force` をそのまま実行していたら、脆弱性対応とCI破損が同じ変更に混ざり、切り分けが難しくなっていました。**AIが出した選択肢のうち、どれが今のプロジェクトの状況に合うかを決めるのは自分の仕事**だと感じた場面です。

詳細は[npm auditで検出したVite脆弱性とnpm ciのlockfileエラーを解消する](npm-audit-vite-lockfile)にまとめています。

## 例2: 公開時にバックエンドAPIをすぐ有効にしなかった

GitHub Pagesへ公開する段階で、フロントエンドにはバックエンドAPIを使うモードと使わないモードがありました。

技術的には、バックエンドを立てて同時に有効化することもできます。しかしその時点でバックエンドは外部未公開で、公開直後に不具合が出た場合、フロントエンドの問題なのかAPI接続の問題なのか切り分けられません。

そのため、まずAPI無効モードで公開する方針にしました。

```yaml
- name: Build
  env:
    VITE_ENABLE_BACKEND_API: "false"
  run: npm run build
```

この状態でも、ゲーム、localStorageへのスコア保存、ランキング表示は動作します。フロントエンド単体で安定して公開できることを確認してから、後日EC2上のAPIを公開し、`VITE_ENABLE_BACKEND_API=true` へ切り替えました。

学習の順番を決めるのは、技術的な最短経路ではなく、自分が何を確認しながら進めたいかです。ここはAIに委ねる部分ではありませんでした。

この切り替えをworkflowへ組み込んだ実装は[Vue + ViteをGitHub ActionsからGitHub Pagesへ自動デプロイする](github-actions-pages-deploy)にまとめています。

## AIへ任せている範囲

一方で、次の作業はAIへ任せた方が速く進みました。

- 既存コードの読み取りと影響範囲の洗い出し
- 実装方針の候補出し
- テスト観点の提案
- エラーログからの原因切り分け
- READMEや開発メモの整理

特に効果があったのは、長くなった作業を「今どこまで終わっていて、次に何を見るべきか」へ分解してもらうことです。個人開発では、実装そのものより作業の現在地が分からなくなることの方が多いと感じています。

## 検証は必ず自分で行う

AIと進めた場合でも、最後の確認は自分で実行しています。

```bash
npm run test
npm run build
npm audit
git status
gh run list --workflow "Deploy to GitHub Pages" --limit 3
```

公開後は、ブラウザで実際にゲームをプレイし、Result表示、localStorage保存、ランキング表示まで見ます。

コードが生成できても、動いているところを自分の目で見ていないと、ポートフォリオとして人に見せられないためです。

## 引き継ぎ資料を残す

AIと長く作業すると会話が長くなり、前提が伝わりにくくなります。そのため、節目ごとに引き継ぎ資料を更新しました。

- 完了した作業
- 未完了の作業
- 次回最初に確認すること
- 重要な設計判断
- 実行済みのテスト
- 失敗したコマンドと原因

特に「重要な設計判断」を残しておくと、次に再開したときにAIへ同じ前提を説明し直す必要がなくなります。

## まとめ

AIを使うと個人開発の速度は上がりますが、出てきた案をそのまま採用するとプロジェクトの目的からずれます。

今回の2例は、どちらも「AIの提案は技術的に正しいが、今のプロジェクトの状況には合わない」ケースでした。`npm audit fix --force` は脆弱性を消しますが変更が混ざります。API即時有効化は動きますが切り分けができません。

やりたいことと進める順番は自分で決め、AIには調査、整理、実装補助、確認手順の作成を任せる。この形が自分には合っていました。
